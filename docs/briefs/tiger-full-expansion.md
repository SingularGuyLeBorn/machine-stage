# 任务书：虎式坦克全车零件扩充（"密集机械"量级）+ git 管理纪律

> **执行者**：任何大模型 / 开发者。背景全靠本文档与项目内 docs/ 提供，无需对话历史。
> **一句话任务**：把虎式坦克从"发动机 L1"推进到"全车密集机械"——**命名零件 250–350、实例零件 2500–3000**，全部进注册表、全部实例级可定位；同时严格执行分批 git 提交，**每条 commit 写清原因**。

---

## 1. 现状与目标

**现状**：`src/three/parts/models/tiger/engine/registry.ts` 已有发动机 L1（62 命名件 / ~250 实例件），框架底座（装配器/穿模检测/构建滑杆/UI）已交付。

**用户判词**（必须正视）："整车零件数不能只有几百——看着像玩具不像真机器。"

**目标量级**：

| 指标                            | 现状 | 目标          |
| ------------------------------- | ---- | ------------- |
| 命名零件（PartDefinition 条数） | 62   | 250–350       |
| 实例零件（含 instances 展开）   | ~250 | **2500–3000** |

**为什么不是越多越好**：锚点是"真机器的可视零件量"（参考 Bovington Tiger 131 实车照片 / Tigerfibel），不是乐高积木数。规格书 3.13.8 密度陷阱仍然有效——**禁止为凑数把大件切稀碎**；本任务的增长全部来自"补真实存在的小件"，不来自"切分已有大件"。

## 3. 硬性原则（违反即返工）

1. **实例化优先**：螺栓/履带销/弹药/弹簧等重复件一律 `instances` + `indexed`，禁止复制零件定义。
2. **禁止凑数切大件**：增长只来自"真实存在的小件"。任何"把一块板切成 N 块凑数"的改动 = 返工（密度陷阱，规格书 3.13.8）。
3. **手册命名**：`name_en` 必须手册原名（德件带德文），树外新零件标注 **[新增]** 并给 `source` 出处。
4. **逐层验收**：每层完成 → 静态穿模零报告 → 截图 → 才进下一层。
5. **tsc / vitest 全绿是常态**：每文件写完即验证；测试只增不减（基线 61）。

## 4. git 管理纪律（用户点名要求）

### 4.1 分批提交（禁止攒大件）

按层提交，一层至少一个 commit；层内大件（如履带系统、弹药系统）可单独成 commit。**工作区未提交改动积压超过一层 = 违规。**

### 4.2 commit message 必须写"原因"

格式：`type(scope): 一句话主题` + **正文写清为什么**（不少于一句"因为/为了"）。

```
feat(tiger): 补全 L1 发动机点火与配气小件（+48 实例）

原因：当前发动机只有大件轮廓，缺火花塞/气门弹簧/点火线等
密集小件，观感被用户评价为"像玩具不像真机器"。本批全部
为实例化重复件（实例 +96，draw call 不增），按 Tigerfibel
与 Jentz 资料补齐；命名件 +14，静态穿模零报告，tsc/vitest 全绿。
```

type 取值：`feat / fix / docs / refactor / test / chore`；scope 用总成名（tiger/engine/track/ui/qa）。

### 4.3 每个 commit 自检三问

1. 这批改动为什么存在？（写进正文）
2. 验收证据是什么？（tsc/vitest 输出、穿模报告数、截图路径）
3. 下一批做什么？（PROGRESS.md 同步更新）
